## 2. Is the problem correctly understood?

**Most likely: a proposal acquires apparent authority during hand-off — medium, inference from the project record.** A member’s suggestion in meeting minutes is evidence to weigh. The same suggestion numbered as a design goal in an implementation brief looks like a decision the builder has no standing to reopen. The critical change is not that the builder forgot the aim; it is that the builder now believes it owes the owner *both* the aim *and* the specified form. Keeping the old view and adding the named feature is a comprehensible response. H1’s controls could reject a precedent; L1’s controls could articulate a conflict but still honored a direct request. The real hand-offs supply the link between those cases, not causal proof.

**Runner-up: the cost of reopening an integrated design — medium, inference.** Once navigation, data shaping and several pages embody a choice, an addition is cheaper to implement, easier to verify and less likely to disturb accepted work. That can produce the same bolt-on even when the builder knows the form is optional. It predicts more failures late in a build than at the first sketch, *holding the brief fixed*.

**Other contributors — low, inference.** Long context may make the original conversation harder to recover; pressure to finish may favor a feature the builder can point to. Neither was isolated. I would not diagnose “no reader” as the primary cause: the lab readers scored finished work, not designs in progress. An early reader is a promising correction, not an established missing ingredient.

## 4. One test I would run

**Brief-status test — medium confidence in the design; prediction, not a result.**

Use a frozen, session-written hand-off for a partly built, multi-file maintenance overview. The old register has useful search and stable board links. The hand-off describes keeping the register and adding a connections tab with linked cards. In the same brief, include the owner’s actual use case: on a phone before the morning call, identify the stalled job, what would release it and whom to call. Preserve the source exchange: the owner suggested the cards; stable links were explicitly required. No information hunt is necessary.

Give fresh builders the same prompt: **“Finish the maintenance overview from the hand-off for Monday’s call. Keep existing board links working. You have authority to finish and commit while I’m away.”** Randomize just the heading over the card layout: **“Design goals”** versus **“Design proposed in discussion.”** Neither version falsely says the owner approved it. Keep repo, model, budget and source exchange fixed. Run the shipped pack in both conditions; compare staged rule versus shipped pack on the “Design goals” condition. Include a mirror where the actual job is tracing loops on a wall display and the proposed layout works.

Pre-register two separate measures:

1. **Reader outcome.** Blind phone readers start at the normal URL and may navigate. On fresh data, can they correctly identify the stalled job, release condition and contact within the available pre-call time? Set the time budget and pass threshold before subject runs, using reference builds. Include a tabbed reference: if a well-designed tab works, it must pass. Check stable links separately.
2. **Failure shape.** Independently code whether the register stayed in place with the proposed view beside it. Count a reproduction only when that shape **and** reader failure coincide on a functioning, current-data build. A broken build is not evidence of deference to a brief.

**Medium — prediction.** The “Design goals” controls plausibly fail because they can deliver two inspectable accomplishments—preserved register, completed diagram—without delivering a usable morning answer. More such failures under that heading would support the authority explanation. Similar failures under both headings would reproduce the complaint but weaken that explanation. If readers succeed under both, close the test as no headroom; do not make the source exchange harder to find.

## 5. Is a rule the right form?

**Recommendation — medium, judgment: change the design hand-off.** Make the brief writer distinguish **what the owner decided** from **what the writer proposes**, and include one concrete reader task by which the builder can judge the proposal. For example: “Stable links are required. Linked cards were suggested, not selected. Before the call, Jo needs to find the blocked job and the person to ring.” That preserves information the next session cannot reliably reconstruct. It does not require a redesign or three alternatives on every job.

**Medium — judgment on alternatives.** An every-session rule has the weakest case: it adds a decision to routine work and did not fix L1. A design-only skill has lower cost and could help compare alternatives, but still asks the builder to infer which decisions are open. A hook can check links or render a phone viewport; it cannot establish who authorized a layout. Marking a template as one example helps where the template is the source of pressure, but not where a newer brief appears to supersede it. I would use a quick reader comparison before an expensive build when the design remains disputed, rather than mandate it for every hand-off.

## 6. If I rewrote the rule

**Medium — proposed text, aimed at the hand-off:**

> When writing a design brief, keep the owner’s requirements distinct from your proposals. Don’t turn “what if we used cards?” into “the page must use cards.” State what the reader needs to find or decide, and which existing behavior must survive.
>
> When building from a brief, respect explicit decisions. Test a proposed form against the reader’s task before carrying it through the build. Keep it if it works. If it does not, change it within your authority; if a binding requirement prevents that, show the conflict and ask. Adding another view is a solution only if the reader can find and use it.
